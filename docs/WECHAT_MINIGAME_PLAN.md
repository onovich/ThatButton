## 目标与首版范围

以当前 Web 游戏为玩法基准，新增可在微信小游戏环境运行的 ThatButton。首版保留规则判断、计时、战斗、连击、Boss、升级、Hazard、结算、失败回顾和本地最佳纪录。界面适配手机触摸与 Canvas 渲染；视觉效果可以按设备性能调整，但不能改变按钮判定或游戏数值。

首版建议使用单机、本地存档、无虚拟支付的范围。登录、好友排行、云存档、分享活动和广告需要各自的产品设计、平台能力与验证，待完整单机局在真机稳定后再排期。正式发布路线和资质以微信公众平台账号后台当时的提示为准。

这里的目标是微信**小游戏**，不是普通小程序页面，也不是用 `web-view` 打开现有网页。阅星曈 `ports/xteink/` 是独立改编版本，不作为小游戏的规则来源。

## 当前基线与影响边界

| 现状 | 对移植的含义 |
|---|---|
| `src/core/`、`src/config/` 保存规则、数值和多数状态计算 | 优先复用，保持不依赖 `wx`、DOM 或 Canvas |
| `src/app/create-app.js` 同时处理游戏流程和 DOM、音效、存档调用 | 先建立行为基线，再逐步提取平台中立的游戏会话 |
| `src/ui/` 和 `index.html` 是浏览器界面 | 保留网页入口；小游戏另建 Canvas 渲染器 |
| `src/host/` 已有版本化输入与事件契约 | 可复用事件语义；它目前不是可直接运行的小游戏引擎 |
| `scripts/build-static-site.mjs` 只复制 `index.html` 与 `src/` | `ports/wechat/` 不进入现有 GitHub Pages 构建产物 |
| `npm run validate` 于 2026-09-28 通过 | 后续每次共用代码改动都要维持通过 |

规划时工作区存在 README、文档和 `ports/xteink/` 的未提交改动；相关内容后续已与微信工程一并合入主线。继续开发时仍须核对实际工作树状态。

建议的代码边界：

```text
src/core/ + src/config/         共用玩法规则与数据
src/app/game-session.js         共用会话：start / press / tick / selectUpgrade / snapshot
src/app/create-app.js           浏览器适配：现有 DOM、音效、存档和 Host/Debug API
ports/wechat/src/              小游戏适配：Canvas、触摸、wx 存档/音效/生命周期
ports/wechat/build/            生成的微信小游戏工程，不作为手工维护的源码
```

提取会话层时，保留网页已公开的 `createApp()`、`__THAT_BUTTON_HOST__`、`__THAT_BUTTON_DEBUG__` 行为及 Host 事件版本。小游戏打包器只负责把共用源码编入小游戏产物，不将微信接口引入网页源码。现有网页构建命令保持原义；小游戏使用自己的构建和验证命令。

## 分阶段实施与验收

### P0：固定网页行为基线

1. 用固定 Seed、固定时间推进和固定输入序列记录棋盘、禁止按键、分数、血量、连击、升级、Hazard、结算与 Host 事件。
2. 覆盖安全按键、误按、超时、Boss 击败、升级选择和本地纪录损坏/恢复。
3. 保存关键手机布局截图，并运行现有 `npm run validate` 与必要的浏览器 smoke。

**通过条件：**同一输入可重复得到同一份状态与事件记录；现有网页仍能完整游玩。

### P1：提取共用游戏会话

1. 从 `create-app.js` 逐段迁移流程，把时间、随机数、存档、事件输出和反馈意图作为显式依赖或输出。
2. 浏览器入口继续调用新的会话层并维持原输入、渲染和音效效果。
3. 每迁移一段就对照 P0 记录。若新增共用模块，更新 `scripts/validate-structure.mjs` 的模块清单，维持原有结构检查。

**通过条件：**固定 Seed 的网页状态、结果和事件与 P0 一致；网页构建、Host/Debug API 和既有验证均通过。

### P2：小游戏可玩纵向切片

1. 创建 `ports/wechat/`，提供 `game.js`、`game.json`、项目配置模板和独立打包命令。
2. 以 Canvas 绘制开始页、提示、棋盘、计时和结算；将触摸坐标映射到稳定按钮 ID。
3. 接入微信本地存储、音效和前后台生命周期。小游戏退到后台时暂停局内时间，返回时恢复。
4. 在微信开发者工具中导入，完成一局开始、按键、失败、重开。

**通过条件：**模拟器能完整跑通最小局；同一输入的规则判定与网页一致。

### P3：完整玩法与真机适配

1. 补齐战斗、连击、Boss、升级、Hazard、最高纪录和失败回顾的画面与反馈。
2. 检查短屏、长屏、安全区域、触摸目标和中文线索可读性；控制动画与音效的设备开销。
3. 用 Android 和 iPhone 真机检查连续多局、切后台、音效恢复、断网和存档重开。

**通过条件：**首版范围中的所有玩法可在两类真机完成；没有被遮挡的关键提示或误触区域；网页回归验证仍通过。

### P4：体验版与发布

1. 用正式小游戏 AppID 上传体验版，邀请体验成员完成试玩并记录问题。
2. 核对名称、图标、类目、适龄提示、隐私保护指引、资质和备案材料。
3. 修复体验版问题，提交版本审核；相关备案与审核完成后，由账号管理员发布。

**通过条件：**体验版、审核通过和正式发布分别留有记录；不能用本地模拟器通过替代真机或平台验收。

## 开工前的准备清单

### 需要项目方决定或提供

- [ ] **账号主体：**确定个人或企业主体，以及小游戏管理员。个人主体能选的游戏子类目有限制；以拟选类目和后台实际提示核对。
- [ ] **开发账号与工具：**在微信公众平台注册小游戏账号，取得 AppID；安装并登录微信开发者工具，将实际开发者加入项目成员。工程基线阶段可先行，体验版上传需要相应账号权限。
- [ ] **正式名称：**确定中文名称、简称与是否保留英文 `ThatButton`。小游戏备案要求名称和账号主体在流程中保持一致，宜在提交备案前定稿。
- [ ] **首版商业模式：**建议先确认“无虚拟支付”。若计划内购，应先核对 IAP 所需出版与支付资质；不要在开发完成后才改变路线。
- [ ] **素材权属：**确认图标、封面、截图、字体和音效均有可用于微信发布的权利。名称含英文或涉及品牌合作时，官方 IAA 资质指引列出了软件著作权或相应授权材料的特定情形。
- [ ] **真机与试玩者：**准备至少一台 iPhone、一台 Android 手机和少量愿意完成整局的体验成员。
- [ ] **上线资料：**准备游戏介绍、玩法说明、宣传图/截图、适龄提示、隐私信息及备案所需的主体资料。具体字段以后台提交页面为准。

### 可以由开发工作先行完成

- [ ] 建立 P0 固定输入与快照基线；盘点网页控制器对 DOM、Web Audio、`localStorage` 和 URL 的依赖。
- [ ] 建立独立小游戏目录与打包脚本；保留现有 Web 构建和阅星曈目录。
- [ ] 提取共用会话并完成网页回归；随后开发 Canvas 适配与模拟器试玩。

**开工门槛：**工程 P0、P1 可以立即开展，不必等备案。正式 AppID 有助于后续真机预览、体验版和上传；账号主体、名称、商业模式与备案材料应尽早确定，以免发布阶段返工。上传密钥、管理员登录信息和身份证明材料不得写入仓库。

WorkBuddy/CodeBuddy 可以辅助编写和检查小游戏代码，是可选开发工具；它们不会代替微信开发者工具中的真机验证、账号权限、资质备案与平台审核。
