# Mac / iPhone 采样独立分析

分析日期：2026-10-02。分析对象：本目录保存的 iPhone 17 原版小游戏 CPU profile；测试业务源码为 `89eab0160cb47aee84bc3f2ac25573688baf6795`。分析时的 `9b5c17f` 与该提交在 `ports/wechat/src`、`src` 下无差异。本报告保留当时的分析和建议，不代表后续优化已经通过真机验收。下文源码行号均对应上述测试基线。本次只分析，没有修改运行代码、配置或微信工具。

## 结论

1. 单次试玩到 48 关、2910 分，用户反馈不卡顿、发热不明显，支持继续小范围玩家测试。它不是长时间功耗验收，也不是优化前后的受控对照。
2. 文字绘制是值得优先验证的候选：`fillText` 有 4,216 个叶采样，全部直接来自项目 `label`；调用来源以局内 HUD、规则区和按钮文字为主。当前缓存的是文字测量结果，不是文字位图，所以有测量缓存仍会反复 `fillText`。
3. `send` 的全部 2,893 个叶采样经过 `syncJsApiCommandBuffer ← flush`。这定位到宿主命令桥路径；不能把它直接解释成网络发送、VPN 开销，或纯调试器开销。
4. `getImageData` 全部来自 `drawGlitchTile`，是明确的局部像素读回候选，但全窗口仅占 1.10% 的归一化采样权重。本次无法判断 glitch 活跃瞬间是否有尖峰，不能据此删除或降级效果。
5. 这份导出最重要的限制：24,670 个时间间隔中，24,669 个完全相同。不能从它算真实 FPS、卡顿分位数、CPU 占用率、阻塞时间或温度。优先做小范围计数与固定场景对照，再决定下一笔优化。

## 输入核验与复核方法

- gzip 解压后 4,073,450 字节，SHA-256：`5df65bc1698e091851e5c7475b4de495b43d85ad1bcbaa6cada8df3c8b76f35e`，与交接摘要一致。
- 9 个 trace 事件；1 个 `ProfileChunk`；21,764 个节点；24,670 个样本和同量 `timeDeltas`。
- 节点通过 `parent` 连接，没有 `children` 字段；一个根节点，没有孤立父引用、缺失样本节点或检测到的循环；最大栈深度 34。
- 对每个样本，用对应 `timeDelta` 累加到被采样节点，得到叶采样权重；沿 `parent` 回溯得到包含子调用的权重。同一栈内相同函数键只计一次，防止重复相加。
- 函数键采用“函数名 + URL”，将同一函数不同采样行位置合并。匿名函数可能因此合并多个函数，不用匿名行作精确优化定位。`label`、`measuredWidth` 等已结合源码确认。
- 可复核脚本：[analyze.cjs](analyze.cjs)。在仓库根运行 `node docs/wechat-mac-test-2026-10-02/analyze.cjs`；从已纳入仓库的 gzip 读取数据，输出到忽略目录 `output/mac-test-2026-10-02/analysis-stats.json`。脚本已纳入版本管理，生成的统计文件不提交。

## 时间间隔的含义与限制

| 项目 | 实际值 |
| --- | --- |
| 首个间隔 | 252 μs，1 个 |
| 其余间隔 | 12,577 μs，24,669 个 |
| 间隔累计 | 310,262,265 μs，即 310.262265 秒 |
| Profile 外壳时长 | 310,458,280 μs，即 310.458280 秒 |
| RunTask / FunctionCall 外壳时长 | 均为 310,258,121 μs |

间隔累计与外壳时长并不完全相等，且数据几乎完全均匀。这与交接中“iOS 适配器生成合成 trace”的说明一致，但不能仅靠该文件还原适配器的具体变换公式。下面的秒数只是导出间隔权重累计；百分比的分母为 310.262265 秒。它们用于识别调用路径，不是各函数实测连续执行秒数。包含子调用的各行互相重叠，不能相加。

尤其不能将 `1000 / 12.577` 视为帧率，不能将外壳 RunTask 的约 310 秒视为卡死，也不能用这份均匀序列计算真实长帧分布。录制还包含试玩前等待，缺少关卡/交互时间标记和真实帧、GPU、内存轨迹。

## 调用来源及源码映射

### 文字

全部 `fillText` 样本的直接父节点均是项目 `label`。其中主要父链（从叶节点向外）：

| 父链 | 样本数 |
| --- | ---: |
| label ← visual ← drawGame | 1,940 |
| label ← drawTile ← 匿名局内绘制回调 | 943 |
| label ← drawGame ← draw | 586 |
| label ← 匿名函数 ← forEach | 373 |
| label ← 匿名函数 ← visual | 340 |
| label ← drawUpgradeV23 ← draw | 12 |
| label ← drawTile ← drawGlitchTile | 12 |
| label ← drawHome ← draw | 10 |

源码映射：`ports/wechat/src/renderer.js` 的 `label`（247 行）、`drawTile`（734 行）、`drawRuleText`（840 行）、`drawGame`（891 行）。`label` 每次设置字体、对齐、基线，必要时描边，最后调用 `fillText`；`drawGame` 包含关卡、分数、规则、倒计时、按钮和状态栏文字。`visual` 是多个元素共用的变换包装，不能只凭其父链就认定全是某一条倒计时文本。

`measuredWidth`（76 行）已有按字体、对齐、方向、文本内容的 Map 缓存，上限 1,024 后清空。其 380 个叶样本里有 341 个来自 `scoreBadge`。这只证明路径常被采到，不能计算缓存命中率，也不能认定 Map 已失效。`measureText` 的叶权重显著小于 `fillText`，暂不优先改测量缓存策略。

### 宿主 send

唯一合并后的完整调用链：

```text
(root) → tt → forEach → 匿名 runtime → 匿名 runtime
       → flush → syncJsApiCommandBuffer → send
```

`flush` 等 URL 均为 `weapp://wechat-game-runtime`，非项目 `wxfs/game.js`。函数命名支持“宿主 JS API 命令缓冲同步”的推断，但没有原生实现或命令明细，无法进一步证明具体是 Canvas、音频还是其他命令。也不能证明 36 秒是纯调试通信成本。减少重复绘制可能减少桥接工作，但须对照验证，不能改桥接或基础库。

### glitch 像素读回

全部 `getImageData` 的父链为 `drawGlitchTile ← 匿名函数 ← visual`。源码 `renderer.js:94–124` 已按 100 ms stamp 缓存目标按钮离屏图，复用 surface 与输出缓冲；缓存未命中时仍重新画按钮、读回像素、做切片/RGB 运算并写回。当前资料没有标出 glitch 活跃区间，所以不能拿全程 1.10% 排除局部峰值。

若后续确有局部峰值，可以验证“缓存不变的原始按钮像素，只重复计算变形输出”的方案；必须完整处理按钮属性、尺寸、按下状态、素材与渲染环境失效，并对比像素与点击区域。此处只提出候选，没有实施。

## __isNativeConsole__ 与断线证据

现有记录支持：错误栈指向 `WAGame.js`，最小探针和原版都出现过；探针 `console.log/warn` 没显示预期日志，而表达式返回值可读；后来原版连接持续并能导出 CPU profile。错误栈没有项目调用帧，这不足以证明游戏触发了错误，也不足以宣布错误无害。

连接摘录中两次 `connectToWkInstance` 到 `FindInstanceTimeout` 分别约 8.863 秒和 8.857 秒；后面有实例发现与连接记录，但没有与 console 错误严格关联的完整时间序列。不能把 console 错误定为断线根因，也不能认定 VPN 是原因。工具升级、后台高性能能力开通和会话重建等变量没有隔离。

不建议硬补 `__isNativeConsole__`、屏蔽错误、改微信基础库或重复盲改网络规则。

## 下一步最小验证与优化顺序

### P0：保留当前可试玩版本，先得到可靠对照

1. 固定业务提交、工具/基础库、手机、亮度、网络和高性能状态。普通预览或体验版不挂调试器、不充电连续玩 10–15 分钟；记录关卡、电量差、发热/卡顿感受。温度未测就写未测。另测挂调试器版本，区分调试和充电影响。
2. 在正确原版 JS 上下文执行各一次有唯一标记的 `log/warn/error` 与表达式返回值，记录是否可见；无持续刷屏。若日志缺失，先用返回值读统计。需要比较基础库时，每次只改这一个变量；不先改业务代码。
3. 如继续做性能优化，在仅内测开启的低频汇总中记录 draw 次数、fillText 次数、文字缓存命中/未命中、glitch tile 重建/读回次数。帧回调间隔可作长间隔代理，但仍不是 GPU 实际呈现 FPS。只汇总，避免逐帧 console 扰动。

### P1：优先验证局内静态文字/规则层缓存

在固定普通局内场景对照 draw、fillText 调用次数及绘制耗时。优先候选是本轮规则、稳定按钮符号/数字、固定标签；动态分数/体力/倒计时依旧及时刷新，动画只变换缓存图层而不改变节奏。离屏文字与直接绘制可能有不同抗锯齿、DPR 或缩放效果，因此不得把“缓存”自动等同于视觉完全一致。

通过后才保留：同一随机种子与操作序列状态一致；固定时间点/不同 DPR 的像素对比；描边、居中、颜色、缩放与透明度效果无变化；触摸命中、计时、换关、后台恢复均回归。内存有明确上限并有失效策略。每项独立、可回退，不降清晰度或帧率。

### P2：按局部证据决定 glitch 进一步缓存

固定同一按钮目标与 glitch 参数，观察该效果活跃前/中/后的读回次数和长间隔代理。只有它确有局部成本才做原始像素缓存；保持 RGB 分离、切片参数、目标选择、持续时长、绘制位置与可点击性完全一致。不能因为本次统计没有峰值就宣布它无性能风险。

### 暂不做

- 不凭这份合成 trace 重构宿主 send、调低 FPS、去掉特效或改变玩法。
- 不把文字缓存预估收益写成已实现收益，不把主观更凉写成量化降温。
- 不以日志基础库错误阻止小范围正常玩家体验，但继续补齐异常采集和 Android/长局验收。
