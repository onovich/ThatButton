## 2026-09-29 可用性修订：高于静态稿

用户复看后提出新的界面要求，实施时以此节覆盖 v12/v13 静态稿中的对应元素：

1. **用按钮实体状态区分按过与未按。** 未按时顶面凸起、侧壁与投影可见；按过后顶面下沉，侧壁缩短、明度/高光减弱。原颜色、形状和数字仍可辨。**不画勾**，也不预先标出安全答案。误按后若本局未结束，该按钮同样进入已按实体状态；错误反馈仅短暂出现。
2. **移除“还剩 X 个安全按钮”。** `safeKeysRemaining` 仍由核心判断清轮，不在常驻界面展示；腾出的空间优先给分数、体力、规则与棋盘。
3. **分数和体力成为主要状态。** 当前分数在页头使用较大的数字/明确层级；体力紧邻棋盘或计时区，用数字和醒目的实际比例条同时显示。连击可以保留为次级反馈。
4. **不常驻展示“威力”“伤害加成”“反击”等数值。** 它们仍参与当前结算：清轮的基础伤害、时间/连击奖励影响 Boss 血量，`combat.attack` 决定误按扣血。UI 以实际分数、体力变化和挑战进度说明结果，无需玩家先读战斗算式。
5. **考官条改为反向积累的“挑战进度”。** 现有 `combat.hp/maxHp` 是原版 Boss 的血量；显示值为 `maxHp - hp`，目标为 `maxHp`，从 0 向满格增长。清完一轮安全按钮会推进这条进度。**用户已确认：每轮照常进入下一关，进度满后进入已有升级选择，再继续下一关。**进度满不是每轮唯一的过关条件。现有分数每按对一次加 10，与该挑战进度仍是两套数值；本次没有要求将两者合并。

### 当前五种升级及精简建议

现在每次击败考官，从下列五种中随机给出三张卡，玩家选一张；当前代码没有内购。

| 当前升级 ID | 实际效果 | 面向玩家的可理解说法 | 已确认处理 |
|---|---|---|---|
| `chain-span-plus` | 连击有效窗口 +500 毫秒，基础窗口 2.4 秒 | 连击接续时间 +0.5 秒 | 保留，效果可在点击节奏中感知。 |
| `max-hp-plus` | 体力上限 +24，当前体力同时恢复 24（不超过新上限） | 体力上限和当前体力 +24 | 保留，直接回应体力主视觉。 |
| `round-time-plus` | 每轮时间上限 +1200 毫秒 | 每轮时间 +1.2 秒 | 保留，直接回应读规则的压力。 |
| `base-attack-plus` | 每次清完一轮，对考官的基础推进量 +4 | 每轮挑战进度额外 +4 | 保留并按反向进度改名；不再称“威力”。 |
| `combo-reward-plus` | 连击达到可见状态时，每次清轮的推进量额外 +1 | 连击清轮额外进度 +1 | 效果小，且与上一项同属进度增益；**从随机池移除**。 |

**用户已确认实施目标为前四种**：微信小游戏的随机池已移除 `combo-reward-plus`，每次仍随机给三张卡；Web 继续使用原池。另一个比卡片数量更值得试玩验证的问题是触发时机：首个考官目标为 500，未升级时每轮基础推进 18、时间奖励至多 4、连击奖励至多 8；即使每轮都拿到上限，首次升级也至少要清完 17 轮。后续应试玩并记录实际抵达时间，再决定是否降低首个目标或加快奖励节奏。

## 现有数据与画面绑定

数据入口是 [`src/app/game-session.js`](../src/app/game-session.js) 调用的 [`ports/wechat/src/renderer.js`](../ports/wechat/src/renderer.js) 接口；[`ports/wechat/src/game.js`](../ports/wechat/src/game.js)负责 Canvas、触摸、存档、音效和前后台时钟。规则、战斗和数值仍归 `src/core/`、`src/config/` 管理，不在视觉层重写。

| 组件或事件 | 真实来源与绑定约束 |
|---|---|
| 首页标题、开始、最高纪录 | 标题固定用“手指等等我”；`updateBestRecordUi(record)` 提供 `bestLevel/bestScore`；开始矩形触发 `app.start()`。角色图不能覆盖点击区。 |
| 关卡、得分 | `renderBoard({level, score})` 与 `updateScore(score)`；每按对一枚安全按钮分数 +10。分数应成为页头主要数字，v13 的“第 16 关 / 320 分”仅是样例。 |
| 禁按规则卡 | `renderBoard.ruleText` 来自 [`src/core/rules.js`](../src/core/rules.js)。完整绘出“且、或、不是”等关系，按 `measureText` 自适应换行，不截为固定两行；强调色只强调原文，不推断或泄露禁按目标。 |
| 棋盘 | `buttons[]` 中的 `id/color.id/shape.id/number/isClicked` 与 `difficulty.rows/cols` 决定 2×2、2×3、3×3。未按下按钮不因 `forbiddenIds` 获得安全/危险外观；已按下保留原颜色、形状和数字，以实体下沉、侧壁缩短和高光变化表达，**不加勾**。黄按钮使用深蓝形状和数字。 |
| 清轮内部状态 | `safeKeysRemaining` 继续决定何时清轮，但不绘“还剩 X 个安全按钮”。删除旧稿的常驻横条，视觉空间让给主要状态。 |
| 本轮计时 | `updateTimer(timeLeft, timeLimit)` 驱动秒数和时间条；切后台的会话时钟由 `game.js` 冻结，视觉动效不能私自改倒计时。 |
| 我方体力与误按 | `updateCombatStatus(getEncounterFacts(state))` 提供 `player.hp/maxHp`，误按反馈取 `lastPlayerDamage.appliedDamage`。数字与比例条在主要信息区显眼呈现；不把 100 HP 画成固定三次机会。 |
| 连击 | `facts.combo.streak/chainCount` 与 `updateTimer` 的 `comboWindow.remainingMs` 可作次级节奏提示；到期及时归零。不常驻显示“威力/伤害加成”；实际清轮推进量仍由 [`src/core/combat.js`](../src/core/combat.js) 计算。 |
| 考官挑战进度 | 原版 `facts.combat.hp/maxHp` 是 Boss 血量；按已确认要求显示 `maxHp-hp` / `maxHp`，清轮时按 `lastDamage.appliedDamage` 增长；满格沿用现有击败/升级节点。`attack` 仍用于禁按误触后的体力扣减，但不常驻显示“反击”数值，也不画成自动定时反击。 |
| 升级 | `showUpgradeScreen({choices})` 给出 `id/type/label/shortLabel/value`，整卡触发 `app.selectUpgrade(id)`；五种现有效果见上表，实施时按用户决定只从前四种抽取三张。中文文案须逐项映射真实效果与单位，不能暗示支付或额外效果。无已批准视觉稿，列为待补资料。 |
| 移动与干扰 | `updateHazardPresentation(hazards)` 含 `phase`、`targetButtonIds`、`motion.offsetXPx/offsetYPx`、`interference.intensity`。同一个最终按钮矩形用于绘制和命中；干扰不得遮挡规则、颜色、形状、数字。 |
| 结算与重试 | `showGameOverScreen({recap,isTimeout})`；`recap.failureReason/level/score/ruleText/pressedButton/safeRemaining/player/lastPlayerDamage/bestAfter` 可支持真实原因与回顾。`timeout` 不显示虚构误按；`wrong_click` 且血量耗尽可写“体力耗尽”。重试触发 `app.reset()`，不标成复活或继续本关。 |

特别核对：当前核心产生的失败原因只有 `timeout` 和 `wrong_click`；误按会调用对手 `attack` 扣血。设计稿提到的独立“对手反击致死”不应在 UI 中编造为第三种已经实现的流程。日后核心若增加失败原因，再单独扩充映射和测试。

## 实施方案与顺序（已启动，待原画验收）

1. **冻结可重复对照。** 保留现有 Web 和微信规则行为；准备固定种子、固定时间的 2×2、2×3、3×3 棋盘及长规则、结束回顾场景。视觉改动只进微信适配层，必要的共用数据补充须保持 Web 回归。
2. **建立可复用绘制层。** 在 `ports/wechat/src/` 中把主题 token、布局计算、文字折行、按钮/条形/卡片绘制、角色资源管理和反馈时序从单体 renderer 分开；保持现有 renderer API 与 `game.js` 的触摸流程。Canvas 先画可玩几何，再接已批准透明图。
3. **先还原最难局内页。** 以 v13 的三种尺寸为排版基准，按上节新要求去掉勾和剩余数，突出分数与体力，重排 3×3 长规则、时间、棋盘和次级连击/挑战进度，再兼容 2×2、2×3。全程使用真实会话值。
4. **接首页与结算。** 首页用 v11 角色和主按钮，结算用 v11 透明双人组及 v12 的“当时别按”；在资源未就绪时保留 Canvas 功能回退。接入图后仍由前端动态绘制标题以外的文字与数据。
5. **补完整流程。** 等升级稿和必要姿态确认后还原升级；再实现清轮、击败、误按、移动/干扰的有限动效。漫画只作为以后可选择的短过渡素材，不新增剧情流程。
6. **按静态、模拟器、真机逐层验收。** 每一阶段维持小游戏集成检查、根项目验证与 Web 行为；最后交运营会话做视觉复验。

布局从实际 `windowWidth/windowHeight/safeArea` 计算逻辑坐标，像素比只用于 Canvas 画布分辨率，触摸坐标仍用逻辑单位；需要同时避让真实平台胶囊和安全区。**不绘 v13 的假系统栏与手机外框。** 在 320×568 的有效区域里优先保证完整规则、至少 56 逻辑单位的题目触控面、九宫格、计时及关键状态；若高度不足，先去掉装饰、缩组间留白与次要标题，再重排状态卡，不裁规则或让局内滚动。390×844 把多出的空间分给规则与棋盘、棋盘与状态卡等内容组，避免全部堆到底部。规则用实测字宽换行并随行数改变卡片高度，尤其覆盖 `rules.js` 的三条件回退和含“不是/或”的句子。

按钮视觉矩形与命中矩形共用同一布局结果；移动 Hazard 在同一坐标上施加位移，弹起、按下、完成的实体外形对应同一材质。弹层出现时只保留弹层命中区域。资源加载须有尺寸、失败回退和重试路径；动画以会话时间/事件为依据，不因每帧重绘叠加计时器。新增 Canvas API 和图片加载后，同步扩展 [`ports/wechat/tests/run.mjs`](../ports/wechat/tests/run.mjs) 的模拟上下文。默认、按下、完成、误按的反馈只在实际操作后发生，不能提前揭示安全答案。
